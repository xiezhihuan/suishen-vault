# 同类项目调研

调研日期：2026-11-23。GitHub API 当时被限流，所以改为浅克隆仓库直接阅读；下表的提交号就是阅读的版本，没有采集星标数。

## 1. 结论

- 就已读到的内容看，没有一个项目同时满足"AI 只能搜到打码信息、用户在 App 上逐条批准、授权码由用户转交、跳板看不到明文"。因此自己实现，只借鉴思路。
- 最接近的是 Bitwarden agent-access（端到端加密 + 不可信跳板）和 loonshoot/agent_vault（逐条人工批准）。前者仍是早期预览、允许同一身份多处在线，后者自己承认同机 AI 可以自我批准。
- 各项目最常见的缺口：AI 能列出全部条目；批准动作发生在 AI 也够得着的地方；批准一次后一段时间内自动放行。本项目三条都不做。
- 许可证：GPL/AGPL 项目（Bitwarden mcp-server、KeePassXC、Passman、Vaultwarden）只借鉴思路，不复制代码。MIT/Apache-2.0 项目目前也没有复制代码；将来若复制，须保留版权与许可声明。

## 3. 逐项分析

### 3.1 Bitwarden agent-access

做法：持有凭据的一端与需要凭据的一端之间跑 Noise NNpsk2，外面套一个 WebSocket 跳板；跳板只按公钥指纹路由，看不到内容。协议文档明确列出跳板能做什么（看到谁和谁通信、消息大小与时间、丢弃、延迟）和不能做什么。README 明说不建议把敏感凭据直接交给大模型，建议用 `aac run` 以环境变量注入进程。

- 借鉴：跳板不可信、只转发密文的总体思路；威胁模型里逐条列"跳板能/不能"的写法；配对令牌自带密钥，避免依赖人眼比对短指纹（文档承认 6 位十六进制指纹只有 24 位熵，可被跳板暴力碰撞）。
- 不适用：同一指纹可同时挂多个连接并都收到消息（`handler.rs` 用 `Vec` 保存同指纹连接），与"只认一个当前设备"冲突。协议标明处于早期预览，接口会变，不作为依赖。Noise 需要自己管理重放窗口和换钥，本项目改用两端标准 TLS 1.3 加公钥固定，工作量和出错面更小。

### 3.2 Bitwarden mcp-server

做法：把 Bitwarden CLI 包成 stdio MCP，提供 `list`、`get`、创建、编辑、删除、设备批准等工具。README 警告只能本机使用，并说明助手可以读到密码。解锁时主密码由系统原生对话框输入，不经过 MCP、模型或命令行参数，并有最小间隔、失败冷却和串行化。

- 借鉴：主密码永远不经过 MCP；解锁尝试的最小间隔与冷却；对话框文案用编译期常量，防止注入。
- 不适用：列出、写入和直接读密码的工具正是本项目禁止的。GPL-3.0，不复制代码。

### 3.3 KeePassXC 与 e4c6/keepassxc-dbus-mcp

KeePassXC 做法：通过 Secret Service（D-Bus）或浏览器扩展协议对外提供条目，访问前可弹窗，逐条勾选允许或拒绝。弹窗里"记住"默认勾选，并有"全部允许且以后也允许"的按钮；请求方可执行文件无法核实时显示警告并自动展开详情。

- 借鉴：批准窗口显示请求方身份并对不可核实的身份给出警告；逐条逐字段决定；可只暴露一部分条目（对应本项目的"对 AI 不可见"）。
- 不适用：默认记住选择、批准以后一直放行。Secret Service 会把用户名、URL、备注和未保护的自定义字段作为属性暴露，超出本项目允许 AI 看到的范围。D-Bus 在 macOS、Windows、Android 上不是通用方案。GPL，不复制代码。

e4c6/keepassxc-dbus-mcp：目前无法访问。只从 [GitHub 主题页的搜索摘要](https://github.com/topics/keepassxc?l=python&o=asc&s=stars)得知它是 Python 写的 KeePassXC Secret Service MCP，更新于 2025-09-11。没有看到源码和许可证，**不从它借鉴任何东西**。

### 3.4 vielhuber/keepassmcp

做法：PHP MCP 服务，经 pykeepass 读写 KeePass 库。`list_entries`/`search_entries` 不返回密码、备注正文和自定义字段值；`search_entries` 会在备注和自定义字段值里匹配；`get_entry` 直接返回机密值，可用 `fields` 缩小范围。主密码从文件读取并经标准输入传给子进程，避免出现在进程参数里。

- 借鉴：搜索结果与机密值分开、按字段缩小返回范围、机密不进命令行参数。
- 不适用：没有用户批准；有列出全部和写入工具；服务端长期持有主密码；在备注正文中匹配会变成逐字猜内容的旁路，所以本项目的 AI 搜索不匹配任何机密字段。

### 3.5 loonshoot/agent_vault

做法：AI 调 `get_secret` 并附理由，服务生成批准链接经 ngrok 打开，用户在手机上点批准，AI 才拿到值。支持按条目或按整个库设置一段时间内自动放行。README 与白皮书明说批准接口没有鉴权，同机 AI 可以自己请求批准页并批准。代码印证：`/approve/:id/yes` 无任何身份校验，首页还会列出全部待批准项。

- 借鉴：AI 必须写理由；审计记录；如实公开局限。
- 不适用：批准走网页且可被 AI 够到。本项目的批准只能在 App 进程内完成，没有任何批准用的网络接口，并且每次要重新解锁。批准后 AI 立即得到值、按时间窗自动放行也不采用。

### 3.6 AuraMaxx（AuraOS / AuraWallet）

做法：本机密钥管理加 MCP。流程是"请求、批准、领取、重试"，领取用一次性编号；审批可按档位授予。`defaults.ts` 中 `trust.localAutoApprove` 默认 `true`，`trust.localProfile` 默认 `admin`，即同一系统用户下经 Unix 套接字接入的进程默认自动批准。会话令牌 strict 档 1 小时，dev/admin 档 7 天。`get_secret` 默认返回打码值，把真值放进 MCP 进程环境或注入指定命令。

- 借鉴：请求与领取分离、领取一次即失效；默认返回打码值。
- 不适用：默认信任本机进程。AI 工具恰好就以同一用户身份运行，本项目把它当作不可信。长会话授权、自带钱包与云端功能不需要。

### 3.7 Passman

做法：Nextcloud 应用，浏览器端用 SJCL 加解密。`encryptservice.js` 中的配置是 AES-CCM、256 位、PBKDF2 迭代 1000 次。

- 借鉴：客户端加密、服务器只存密文。
- 不适用：迭代次数远低于现在的通行建议，改用 Argon2id；依赖 Nextcloud 服务器，与"单主设备、无中心服务器"不符。AGPL，不复制代码。

### 3.8 Vaultwarden

做法：Bitwarden 兼容的自托管服务器，面向多端同步。`THREAT_MODEL.md` 写明服务器能读到的全部非加密内容（如组织名、邮箱、时间戳、附件大小），也写明控制服务器的人可以下发被改过的网页端，使端到端加密对网页端用户失效。

- 借鉴：威胁模型按"参与者、能碰到什么、不该碰到什么"组织；如实列出超出范围的情况；反代日志会记下 URL 里的令牌这一教训（对应本项目授权码禁止进 URL）。
- 不适用：多端同步与账号体系不需要。AGPL，不复制代码。

### 3.9 frp

做法：通用内网穿透。stcp 类型需要访问方也运行 frpc 并持有共享密钥；登录校验值由令牌与时间戳做 MD5 得到，用常量时间比较；`control.go` 按 runID 管理控制连接，登记新连接时会处理同一 runID 的旧连接。frpc 默认开启 TLS，但在没有配置 CA 时**不校验服务器证书**。

- 借鉴：设备主动外连、服务器只做转发的结构；同一身份只保留一个控制连接。
- 不适用：身份替换按 runID 而不是按可轮换的所有者密钥，无法表达"迁移后旧设备永久失效"；服务器配置自由度大，用户容易误配成对外暴露明文端口；访客密钥校验处用普通不等比较，本项目统一用常量时间比较。
- 结论：自己写一个只做一件事的 `vault-relay`。用户若已在用 frp，也可以只拿它给 `vault-relay` 的端口做 TCP 转发，安全性不依赖 frp。

## 4. 协议与客户端现状

### 4.1 MCP 规范

当前正式版是 [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog.md)，上一版是 [2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog.md)。与本项目有关的变化：

- 取消 `initialize` 握手和 `Mcp-Session-Id`，每个请求在 `_meta` 里自带版本与能力；跨调用状态由服务器签发句柄，作为普通参数传递。
- 服务器必须实现 `server/discover`。
- POST 必须带 `MCP-Protocol-Version`、`Mcp-Method`，`tools/call` 还要带 `Mcp-Name`，与正文不一致时返回 400 和 `-32020`。
- 取消独立 GET 流与 SSE 断点续传。
- 服务器必须校验 `Origin`，存在且不合法时返回 403；本机运行应只绑定回环地址。
- [鉴权](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization.md)对实现是可选的；HTTP 传输若要支持则应遵循其 OAuth 2.1 规则；stdio 传输不应使用它，应从环境取凭据。
- 服务器可以[同时支持新旧两代](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md)客户端。

### 4.2 客户端鉴权方式

| 能力 | Claude Code（[文档](https://code.claude.com/docs/en/mcp)） | Codex（[文档](https://learn.chatgpt.com/docs/extend/mcp)） |
|---|---|---|
| stdio | 支持 | 支持 |
| Streamable HTTP | 支持 | 支持 |
| 静态请求头 | `--header` / `headers`，可用 `${VAR}` 展开 | `http_headers`、`env_http_headers` |
| Bearer 令牌 | 通过 `Authorization` 头 | `bearer_token_env_var` |
| 由本机命令产生请求头 | `headersHelper` | `http_headers_helper` |
| OAuth | 支持 | 支持，`codex mcp login` |
| 2026-07-28 | v2 运行时支持，不支持的服务器自动退回旧版 | 源码 `rmcp-client` 已处理新旧两代（读的是 [a1604a8](https://github.com/openai/codex/tree/a1604a8c0554c09c1be45e5a121bb1889b4d9a50)，Apache-2.0；文档未写协议版本） |
| 工具调用超时 | 可按服务器配置 | `tool_timeout_sec`，默认 60 秒 |

两点需要在设计里注意：

- Claude Code 若配置了 `Authorization` 头且被拒绝，会直接报连接失败，不退回 OAuth。
- 曾有 Claude Code 不发送 `headers`/`headersHelper` 的问题报告（[#48514](https://github.com/anthropics/claude-code/issues/48514)、[#59467](https://github.com/anthropics/claude-code/issues/59467)，只看了搜索摘要）。stdio 桥接不受这类问题影响，这是把它设为推荐接入方式的原因之一。

### 4.3 Rust SDK

官方 [rmcp](https://crates.io/crates/rmcp) 3.11.0，Apache-2.0，看过源码片段。已含 2026-07-28 与 2025-11-25 两个版本；`legacy_session_mode` 可关闭会话。**注意**：它的 `allowed_origins` 默认是空列表，注释说明空列表会关闭 Origin 校验，所以本项目必须在它外面自己加一层 Origin 与 Host 校验。
